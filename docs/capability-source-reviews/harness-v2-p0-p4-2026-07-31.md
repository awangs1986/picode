# Harness V2 P0–P4 Capability Source Reviews

Date: 2026-07-31  
Owner: Picode  
Scope: the eight confirmed Harness V2 module Interfaces in [P0-P5-HARNESS-V2](../P0-P5-HARNESS-V2.md).

This file contains a separate review for each capability being implemented. It is not a generic source inventory. Existing Picode implementations are reused behind the new Interfaces wherever they already satisfy the behavior.

## CSR-HV2-01 RuntimeSpine

- **Pi ecosystem:** Pi extension lifecycle events and RPC are the retained model/runtime integration. They do not provide one Picode-owned durable lifecycle across Tauri, broker, external work, evidence, and imported sessions.
- **Oh My Pi:** the prior [OMP runtime alignment](../research/omp-runtime-alignment.md) shows useful persistent process and task lifecycle behavior, but copying its runtime would duplicate Pi and violate Picode's embedding constraint.
- **Comparable agent:** grok-build `dd04f397` provides typed session/tool/subagent/compaction lifecycle and stop gates; its [hooks dispatcher](https://github.com/xai-org/grok-build/blob/dd04f397b1d02f2272b092555669dfba1f01bc85/crates/codegen/xai-grok-hooks/src/dispatcher.rs) is Apache-2.0. We reuse behavior, not code.
- **Decision:** deepen existing `runtime_coordinator.rs` and `runtime_registry.rs` behind a Picode Interface. Clean-room Rust implementation. Resident control-plane only; bounded event payloads.

## CSR-HV2-02 SessionKernel and transports

- **Pi ecosystem:** Pi remains the native live-session implementation and session format. Picode must additionally normalize imported Codex/Cursor/Claude snapshots, archive/delete/backup state, and multi-process identities.
- **Oh My Pi:** session/checkpoint behavior is useful as a reference, but not a standard client protocol.
- **Comparable agent:** grok-build's [sessions](https://github.com/xai-org/grok-build/blob/dd04f397b1d02f2272b092555669dfba1f01bc85/crates/codegen/xai-grok-pager/docs/user-guide/17-sessions.md) and [ACP mode](https://github.com/xai-org/grok-build/blob/dd04f397b1d02f2272b092555669dfba1f01bc85/crates/codegen/xai-grok-pager/docs/user-guide/15-agent-mode.md) validate append-only updates and a shared IDE/headless transport. ACP itself is an open protocol.
- **Decision:** keep Pi JSONL as native transcript, use Picode SQLite/event records as the cross-source index, and implement a clean-room ACP Adapter over the existing broker. No grok runtime code copied.

## CSR-HV2-03 WorkManager

- **Pi ecosystem:** `pi-subagents` 0.37.2 and Pi tools already expose child/background work; Picode already owns OS processes through `PiManager`, `OrchestrationService`, and `ExtensionService`.
- **Oh My Pi:** persistent shell/eval and supervised jobs were already adapted in the P0–P4 baseline.
- **Comparable agent:** grok-build's per-session [background registry](https://github.com/xai-org/grok-build/blob/dd04f397b1d02f2272b092555669dfba1f01bc85/crates/codegen/xai-grok-shell/src/terminal/background_task.rs) confirms a unified handle/status/wait/kill shape.
- **Decision:** deepen existing Picode process managers into one observable handle model. Windows Job Object support is Picode-specific because grok-build's repository is not a tested Windows implementation.

## CSR-HV2-04 CompletionEngine

- **Pi ecosystem:** Pi tools can run checks but do not define Picode's Red-capable Gate, Evidence Ledger, completion labels, or CI authority split.
- **Oh My Pi:** acceptance and tool evidence informed the existing baseline; it does not supersede Picode's red-probe rule.
- **Comparable agent:** grok-build Stop hooks demonstrate lifecycle-enforced completion, but hook failures are fail-open and therefore insufficient as verification authority.
- **Decision:** deepen the existing `harness.rs` Gate Validity and ledger implementation; use RuntimeSpine `BeforeComplete` as the seam. Picode remains stricter than the reference.

## CSR-HV2-05 ContextEngine

- **Pi ecosystem:** Pi owns provider messages and native compaction hooks; `pi-subagents` owns child contexts. Picode's existing `context_compression.rs` is for user-created portable packages, not live turn budgeting.
- **Oh My Pi:** aggressive pruning/checkpoint concepts are relevant but its full runtime is not adopted.
- **Comparable agent:** grok-build's Apache-2.0 [token fit ladder](https://github.com/xai-org/grok-build/blob/dd04f397b1d02f2272b092555669dfba1f01bc85/crates/common/xai-grok-compaction/src/intra_compaction/fit.rs) verifies deterministic old-turn selection and oversized tool-result trimming.
- **Decision:** implement an independent Picode fit policy over normalized items, retain full content as Evidence Artifact, and leave semantic/durable memory disabled. No source copied.

## CSR-HV2-06 CodeIntelligence

- **Pi ecosystem:** prefer Pi LSP extensions when available. Existing Picode `CapabilityService` already supplies lazy mappings and framed LSP transport.
- **Oh My Pi:** its lazy LSP/DAP behavior informed the existing implementation.
- **Comparable agent:** grok-build's [LSP manager](https://github.com/xai-org/grok-build/blob/dd04f397b1d02f2272b092555669dfba1f01bc85/crates/codegen/xai-grok-tools/src/implementations/lsp/manager.rs) confirms version-aware diagnostics, bounded summaries, restart, and process-scope cleanup.
- **Decision:** deepen the existing lazy LSP manager; do not add a second server stack. Preserve zero process startup for Simple Tasks and unused Harness capabilities.

## CSR-HV2-07 DelegationEngine

- **Pi ecosystem:** adopt the already pinned `pi-subagents` 0.37.2 for chain, parallel, fork, resume, structured output, acceptance, and worktrees. This is the selected implementation, as recorded in [the dedicated comparison](../research/pi-subagents-comparison.md).
- **Oh My Pi:** no need to copy its task runtime after a suitable Pi extension was found.
- **Comparable agent:** grok-build's capability modes, persona contracts, worktree resume, and one-level default provide UX/state references only.
- **Decision:** write only the Picode Adapter that maps GUI model/account policy, RuntimeSpine ownership, Evidence candidates, Safe Worktree, and controls to pi-subagents. Do not reimplement orchestration.

## CSR-HV2-08 ExtensionManager

- **Pi ecosystem:** Pi extensions, Skills, MCP and the pinned packages remain the executable implementations. Picode already has `CapabilityService` and `ExtensionService`.
- **Oh My Pi:** its extension discovery and lazy devices informed the three-tier baseline.
- **Comparable agent:** grok-build's [plugin model](https://github.com/xai-org/grok-build/blob/dd04f397b1d02f2272b092555669dfba1f01bc85/crates/codegen/xai-grok-pager/docs/user-guide/09-plugins.md) validates separate discovered/enabled/trusted/running states, component inventory, project trust, and SHA pinning.
- **Decision:** deepen existing Picode catalogs into one four-state Interface. Keep third-party executable components disabled by default. Reuse no grok code; preserve each Pi package's own license and notices.

## CSR-HV2-09 Lifecycle Hooks

- **Pi ecosystem:** Pi extension events remain the lifecycle source; hooks do not replace Pi tools or permissions.
- **Oh My Pi:** its hook-style lifecycle automation is useful as a behavior reference, but Picode already owns authorization and process supervision.
- **Comparable agent:** grok-build Stop hooks confirm matcher/timeout/result semantics, while their fail-open behavior is intentionally not accepted as verification evidence.
- **Decision:** implement a small Picode Hook Manager that delegates command execution to WorkManager. Hooks are Disabled User Modules, require separate enable and trust actions, and a failed or skipped hook can never upgrade CompletionEngine evidence.

## CSR-HV2-10 Git checkpoint, rewind, and handoff

- **Pi ecosystem:** Pi supplies the coding loop but does not own Picode's Git safety and developer-to-CI handoff format.
- **Oh My Pi:** its checkpointing confirms Git-first recovery for engineering work; copying its runtime is unnecessary.
- **Comparable agent:** grok-build's worktree/resume workflow validates preserving the original tree and carrying explicit recovery metadata.
- **Decision:** deepen the existing Picode `GitSnapshot` and Safe Worktree implementation. Rewind is clean-tree-only, previewed, fingerprint-bound, exactly confirmed, and implemented as a non-history-rewriting `git restore` from a commit. Handoff stores references and bounded summaries, never project files.

## Shared security, maintenance, and cost decision

- No reviewed source replaces the embedded Pi runtime.
- New first-party code is clean-room and remains under Picode's MIT license.
- Any later source copy requires a file-level license/NOTICE review; this document authorizes behavioral adaptation only.
- Resident additions are schemas and state machines. LSP, MCP, DAP, browser, evaluator, firstmate, hooks, memory, scheduler, and remote workers remain lazy or disabled.
- Tests use in-memory/local adapters at the confirmed Interfaces. External providers are mocked only at their true network boundary.
